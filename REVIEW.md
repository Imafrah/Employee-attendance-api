# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | Checked `minutes > 10` after integer floor division rather than checking whether elapsed seconds strictly exceeded 600 seconds (R2). Also formed shift start directly on punch-in without converting from UTC to IST (R1). | At 09:40:01 for a 09:30 shift, elapsed time is 601s; `int(601/60)` is 10, and `10 > 10` returned 0 instead of 10. Also caused timezone offset calculation errors. | Converted punch-in to IST, created shift start datetime in IST, checked `if diff_sec > 600: return diff_sec // 60 else: return 0`. |
| 2 | `compute_work_hours` (lines 40-41) | Used Python's built-in `round(..., 2)`, which implements banker's rounding (round-half-to-even) with floating-point errors, violating R4 (half-up rounding). Also did not truncate timestamps to whole seconds (R1). | Duration of 2.525 hours rounded down to 2.52 instead of rounding up to 2.53. Millisecond jitter was not truncated to whole seconds. | Truncated instants to whole seconds and implemented `round_half_up` using `decimal.Decimal` with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` (lines 44-47) | Did not handle overnight shifts where `shift_end <= shift_start` (R1), causing `shift_end` to be evaluated on the same calendar date rather than the next day. Also did not enforce the 30-minute minimum threshold per R3. | Overnight shift 22:00–06:00 on 2026-07-06 with punch-out at 06:40 on 2026-07-07 produced 1480 overtime minutes instead of 40. Punches with <30 min overtime were counted. | Added check: if `shift_end <= shift_start`, `shift_end` is shifted to the next calendar day (`+1` day). Enforced `diff_sec >= 1800` (>= 30 min), otherwise returning 0. |
| 4 | `GET /health` (lines 72-74) | Unconditionally returned `{"status": "ok"}` with 200 without checking database connectivity, violating the requirement to return 503 if MongoDB fails a ping. | Stopped or disconnected MongoDB; calling `GET /health` still returned 200 OK instead of 503. | Added `client.admin.command("ping")` in a try/except block; on error, raised `HTTPException(503, "Database unavailable")`. |
| 5 | `POST /employees` (lines 77-85) | Used check-then-insert (`find_one` then `insert_one`), susceptible to race conditions. Stored naive `datetime.now()` instead of UTC BSON date, returned non-serializable datetime or missing epoch ms, and did not validate `shift_start != shift_end`. | Concurrent employee creation with the same `emp_code` created duplicates or failed with unhandled errors. Schema validation failed on `created_at`. Equal shifts were accepted. | Added unique index on `emp_code`, caught `DuplicateKeyError` to return 409, validated `shift_start != shift_end` with 422, stored UTC datetime and serialized `created_at` as epoch ms. |
| 6 | `GET /employees` (line 93) | Pagination skip was calculated as `skip = page * page_size`. For page 1, `skip = 1 * 20 = 20`, skipping the entire first page of results. | Requesting `GET /employees?page=1&page_size=20` returned records 21-40 rather than 1-20. | Corrected skip calculation to `skip = (page - 1) * page_size`. |
| 7 | `GET /employees` (line 94) | `total` count query was hard-coded to `{}` (`db.employees.count_documents({})`), ignoring the `department` query filter, violating R10. | Querying `GET /employees?department=Engineering` returned a `total` equal to company-wide headcount rather than Engineering headcount. | Changed to `db.employees.count_documents(q)`. |
| 8 | `GET /employees` (line 95) | Missing sorting. The API contract explicitly requires the list to be sorted by `emp_code` ascending. | Employees were returned in natural insertion order or non-deterministic order. | Added `.sort("emp_code", 1)` to the MongoDB query cursor. |
| 9 | `POST /attendance/punch-in` (lines 100-101) | Did not check if employee existed. If `emp` was `None`, line 113 crashed with `TypeError: 'NoneType' object is not subscriptable` (500 Internal Server Error) instead of returning 404. | Calling punch-in with an unregistered `emp_code` triggered an unhandled 500 server crash. | Added existence check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 10 | `POST /attendance/punch-in` (lines 104-105) | Used check-then-insert (`find_one` then `insert_one`), failing under concurrency. Two simultaneous punch-in requests both inserted records for the same employee and date. | Concurrent punch-in requests resulted in duplicate records and race conditions rather than one 201 and the rest 409. | Added unique compound index on `("emp_code", 1), ("date", 1)` and caught `DuplicateKeyError` to return 409. |
| 11 | `POST /attendance/punch-in` (lines 102-103) | Attendance date was computed directly as `ts.date().isoformat()`. For overnight shifts (R1), early morning punches belong to the previous day's shift. | An employee on a 22:00–06:00 overnight shift punching in at 05:30 IST had the punch recorded under today's date instead of yesterday's date. | Implemented `get_attendance_date` to check if `shift_end <= shift_start` and punch-in time in IST is strictly before `shift_end`, subtracting 1 day if so. |
| 12 | `POST /attendance/punch-in` (lines 118-121) | Injected an extraneous `"id"` field (`str(res.inserted_id)`) not present in the OpenAPI schema, and returned unformatted datetime objects instead of integer epoch milliseconds. | Contract validation failure on response schema; extraneous `"id"` returned and `punch_in` was not integer epoch milliseconds. | Removed `"id"`, converted BSON datetimes to epoch milliseconds, and formatted output strictly according to `AttendanceRecord`. |
| 13 | `GET /attendance` (lines 144-147) | Loaded all matching records into Python memory with `list(db.attendance_logs.find(q))` and sorted in Python (`docs.sort(...)`), causing memory exhaustion and massive latency at 100k records. | Testing against 100,000 documents caused high memory usage and slow response times; explain plan showed in-memory sort and lack of index-assisted pagination. | Replaced in-memory operations with database-level `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` backed by compound indexes. |
| 14 | `GET /attendance` (lines 136-146) | Did not validate `date_from > date_to` (must return 422), and only sorted by `date` reverse in Python, missing the required tie-breaking sort on `emp_code` ascending. | Passing `date_from=2026-07-20&date_to=2026-07-01` returned 200 with an empty list instead of 422. Records with identical dates lacked deterministic sorting. | Added check: `if date_from and date_to and date_from > date_to: raise HTTPException(422)`. Sorted by `[("date", -1), ("emp_code", 1)]`. |
| 15 | Startup / Indexes (entire file) | Did not create any database indexes. Both collections relied only on the default `_id` index. | Running explain on list and analytics endpoints resulted in `COLLSCAN` across all collections; unique constraints could not be enforced under concurrency. | Created idempotent indexes in FastAPI lifespan for `emp_code`, `department`, `joined_on`, and `(emp_code, date)` compound keys. |

---

### What was examined and decided was NOT a defect:
1. **Storing derived fields directly on documents**: We verified that storing `work_hours`, `late_minutes`, `overtime_minutes`, and `half_day` directly on `attendance_logs` documents is intentional per `DATA_MODEL.md` ("Stored derived values are authoritative"). Analytics are defined to read these stored values rather than recomputing them from punch times.
2. **`punch_out` being `null` on punch-in**: OpenAPI contract explicitly specifies `punch_out` and `work_hours` start as `null` until punch-out occurs.
3. **Default status `PRESENT`**: Punch-in defaults to `PRESENT` unless explicitly specified as `WFH` or `ON_DUTY`, which matches `openapi.yaml`.
